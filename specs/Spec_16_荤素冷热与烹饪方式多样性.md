# Spec_16 荤素冷热与烹饪方式多样性

## 一句话目标

> 为正式菜谱补齐可审核的搭配属性，并在不影响硬约束和营养目标的前提下，优先生成荤素、冷热及主烹饪方式更合理的菜单。

## 数据模型

全部 1912 道正式菜谱必须包含以下字段；菜单规划仍只使用其中 `is_recommendable=true` 的菜谱。

| 字段 | 类型 | 约束 |
|---|---|---|
| composition_type | string | 必填；只允许荤、素；含肉类或水产即为荤，只有蛋奶仍为素 |
| serving_temperature | string | 必填；只允许热、冷，表示典型食用温度 |
| primary_cooking_method | string | 必填；只允许蒸、煮、炒、炖、煎、炸、烤、拌、烧焖、冷制、其他 |

荤素依据标准食材分类确定。冷热和主烹饪方式由两套独立 LLM 提示离线标注；两次结果均为高置信且完全一致才自动通过，其余结果必须经人工审核后才能写回正式数据。

## 端点 / 接口

| 动作 | 输入 | 成功返回 | 失败情况 |
|---|---|---|---|
| 菜谱属性 generate / validate / apply | 正式菜谱、标准食材分类、双提示结果、人工审核结果 | 1912 道菜的完整属性并原子写回 | 缺项、重复、非法枚举、未完成审核或源数据变化时拒绝写回 |
| `sync_recipe_pairing_attributes` | 已通过完整校验的正式 JSON | 原子写回 JSON，事务回填 PostgreSQL 并收紧约束，事务更新 Neo4j | 任一步失败立即退出；可幂等重复执行 |
| 应用启动一致性校验 | JSON、PostgreSQL、Neo4j | 1912 道菜的名称和三项属性逐菜一致才继续启动 | 缺列、缺菜、多菜、非法值或不一致时拒绝启动 |
| MenuPlanningService.plan | 带三项属性的原规划输入 | 按新增软目标选出的唯一最优菜单 | 属性缺失或非法返回 400；原有无解、超时和内部错误不变 |
| `/v1/chat/completions` | 原请求字段 | 原响应结构，回答增加搭配说明 | HTTP 字段、状态和 SSE 格式不变 |

## 边界（每条之后会变成一条测试）

- 任一食材类别为肉类或水产时判为荤；只有蛋奶且无肉类、水产时判为素。
- 食材不在标准分类表、类别缺失或非法时拒绝分类并返回400，不调用模型猜测。
- 双提示均为高置信且冷热、主做法完全一致时自动通过；任一低置信或任一字段不一致时进入人工审核。
- 审计输入必须与源数据的 1912 个菜名、顺序和源数据哈希一致；模型输出缺项、多项、重复、乱序或非法枚举返回502，不重试、不切换模型。
- 1912 道菜任一缺项、重复、非法枚举或人工项未完成时不得写回；相同结果重复应用内容不变。
- 所有人工项完成前禁止执行同步；同步前必须完成全部校验，JSON 使用临时文件原子替换，PostgreSQL 和 Neo4j 各在事务内按菜名更新。
- 正式 JSON、PostgreSQL 和 Neo4j 的三项属性必须逐菜一致；应用在创建 LLM 和业务服务前只读校验三方，不一致不自动迁移或修复，缺失属性不得运行时推测或使用默认值。
- 荤素和冷热统计整份已选菜单，包含菜、汤、主食、小菜和甜品。
- 菜单少于 2 项时荤素目标不参与选优；2 项起先最小化荤素数量差，差相同时优先素菜较多的菜单。
- 菜单少于 4 项时冷热目标不参与选优；4 项起优先至少有 1 项冷菜且热菜数量多于冷菜的菜单，不要求固定比例。
- 荤素和冷热结果相同时，主烹饪方式种类更多的菜单优先。
- 完整优先级固定为：硬约束、营养得分高、异常营养项少、荤素、冷热、主做法种类多、标签命中多、候选顺序靠前。
- 三项搭配均为软目标，不得使原本可行的菜单无解，也不得覆盖换菜、保留和排除约束。
- 回答必须说明实际的荤素数、冷热数和主做法列表；未达到软目标时不得表述为“已达标”。

## 明确不做（划出范围，防 AI 自由发挥）

- 不解析“两荤两素”“一冷三热”等用户指定比例。
- 不把荤素、冷热或烹饪方式升级为硬约束。
- 不保存多种烹饪方式，不在运行时调用 LLM 标注。
- 不修改现有营养、健康、菜品类型、推荐资格或换菜规则。
- 不新增 HTTP 字段、端点或改变 SSE 格式。
